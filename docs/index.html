WHAT BROKE, WHAT I DID
MALFORMED INPUT

One bad frame took everything down

A device sends something malformed inside an aggregated batch. Reject the batch and you lose every good event in it; let it through and the listener dies, taking ten thousand connections with it.

I moved validation to per-event: bad events are isolated, counted and left behind while the rest of the batch continues. Thread-safe concurrent sessions, configurable limits and timeouts, and every source identifier preserved through normalisation so a problem traces back to the device that caused it.

LISTENER STAYS UP · 10,000+ CONCURRENT STREAMS
RACE CONDITION

Two guests, one property, same instant

Booking logic that reads correctly in review double-books under concurrency. The transaction path was also taking over two minutes, which widened the window every time.

I re-engineered the booking path to make the conflict impossible rather than unlikely, and cut the latency that was making it worse.

2 MIN → UNDER 2 SEC · DOUBLE-BOOKINGS STOPPED
RECOVERY

A backup nobody has restored is not a backup

Most teams have a backup schedule. Far fewer have ever restored one into a clean server and watched it come back.

I own backup and restore for self-hosted MongoDB replica sets and PostgreSQL across a 10–20 server estate on AWS EC2, with Grafana monitoring across it. The restores are tested, which is the only version of the sentence that means anything.

RESTORES VERIFIED, NOT ASSUMED
SCALE

Search that timed out at 15,000 listings

Queries were failing rather than slowing. Indexing strategy, filtering and sorting rebuilt, plus an image pipeline — WebP, compression, lazy loading, CDN caching — so pages stopped waiting on media.

TIMEOUTS → UNDER 3 SEC
